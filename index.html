The risk

The category that causes the most breaches is the one nobody decides

Broken Access Control is #1 in the OWASP Top 10 for 2025; Security Misconfiguration is #2. Both are application-layer defects — what an app's own roles and settings permit, which the cloud beneath it never sees. Neither is exotic, and neither is being designed out.

And they live for years

Each of these was authenticated, well-formed traffic to an endpoint the caller was allowed to use. That is what this class of defect looks like from the outside — which is precisely why monitoring did not stop it.

A defect class present in every tested application, invisible to automated tooling on both sides of the contest, surviving for years once introduced — is not a remediation problem. It is a design-time problem, and it needs a design-time answer.

Why it persists

Every technique in common use either guesses the intended policy, or has a person hand-write it

This is not a criticism of any individual tool — each answers a different question, and answers it well. The point is narrower: none of them holds a statement of who is supposed to be able to do what, and none reads the application's own role configuration.

Static analysis

SAST

Flags a route with no recognisable authorisation decorator. It cannot know the intended policy, so a check that is present but wrong — inverted logic, the wrong role, the wrong object — reads as correct.

Blind to · authorisation configured at runtime
Dynamic testing

DAST

With several personas it will replay one user's requests as another and compare. Strong, and still a sample: it tests the endpoints someone crawled, against the data someone seeded, outside production.

Blind to · endpoints never crawled
Dependencies

SCA & supply chain

Finds known CVEs and known-bad packages. It cannot judge whether a legitimate plugin's permissions suit your policy, or whether a vulnerable feature is switched on in configuration.

Blind to · plugin permission grants
Cloud posture

CSPM & CNAPP

Traces lineage from repository to running workload and ranks findings by cloud context. Its attack path reads exposed workload → vulnerable package → IAM role. It stops at that role.

Blind to · the app's own role model
Runtime

WAF & API monitoring

Matches known attack shapes and baselines per-user behaviour. A broken-access request is well formed, authenticated, and aimed at an endpoint the caller may use — there is no payload to match.

Blind to · the request that looks legitimate
Human

Penetration testing

Finds more logic bugs than any other technique, and the bug-bounty growth in this category is human-found. But it is point-in-time, scoped, and testers infer intent rather than being told it.

Five blind spots they share

These are structural limits of the methods, not gaps that a better product release will close.

 Blind spotWhy it cannot be closed from inside the method
B1No statement of intended policyEvery tool substitutes a signature, a baseline, a schema or a tester's tick-box. None of those is intent.
B2The app's own roles are invisibleA self-hosted application keeps role-to-resource grants in its own database and admin panel. Code, infrastructure and cloud scanners all read somewhere else.
B3Nobody composes the layersCloud tools stop at the IAM role; application tools stop at the application. The path between them belongs to neither.

A monitor sees what happened. Not what could. An access-control defect is a reachable bad state whether or not anyone has reached it yet — and the dormant endpoint that generates no traffic generates no finding either.

What AI changed

More dangerous, more numerous, and still invisible to automation

The interesting finding is not that attackers have AI. It is that the entire AI wave — offensive and defensive — is washing over this specific defect class without touching it.

One · attackers automated it

  • In a state-sponsored campaign disclosed in late 2025, AI performed 80–90% of the tactical work across roughly thirty targets
  • Reconnaissance, credential access and lateral movement are authorisation problems
  • That operating model has since spread to every class of actor

What changed was the economics of the attack, not the techniques.

Two · AI writes the apps

  • AI-generated code security has stalled at a 56% pass rate across two years and a hundred models
  • Models now handle the mechanical classes well — SQL injection, cryptography
  • Authorisation is not even in the benchmark, because it cannot be checked from a file

When three leading agents each built full applications, broken access control was the most universal flaw in every one.

Three · and AI cannot find it

  • 0% — the strongest model's success rate on authorisation logic spread across multiple files
  • 0% — the same, on framework middleware, which is where real authorisation lives
  • 88% of what it did report was false
A model can spot a missing check where one obviously belongs. It cannot decide whether a distributed authorisation scheme is correct.

The agent problem is this problem. An AI agent's effective permissions are the transitive closure of its tool graph, not the union of its individual grants — the same composition question, arriving in a new form. AWS's own answer secures agent permissions with Cedar: the same analysable language, and the same symbolic analysis, that our method applies to the application layer.

A scanner knows cross-site scripting when an alert box pops. It cannot know whether user 7 was supposed to read order 1002 — because that fact is not in the code, the traffic or the response. It is a business intention, and until it is written down in a form a machine can check, no amount of model capability will find it.

The method

This is not an unproven technique. It runs at cloud scale today.

Automated reasoning compiles a policy into logic and decides a property over every possible request, rather than sampling. Three systems, all published, all in production, all from AWS.

FMCAD 2018

Zelkova

Compiles an access policy to SMT and decides a property over every request context — principal, action, resource and condition keys. Behind IAM Access Analyzer and S3 Block Public Access.

An authorisation language built to be analysed. Proves a policy set always allows, always denies, is equivalent to or implied by another — and returns a counter-example when it does not.

Sound and complete · proved in Lean · Apache 2.0 · CNCF

Tiros

Decides whether a network path exists between two points, from the configuration alone, without sending a packet. Behind VPC Reachability Analyzer and Network Access Analyzer.

The industry proved that access policies can be decided rather than scanned, then stopped one layer short of where the risk actually lives. The languages and the solvers are open and free for commercial use. What is missing is the translation and composition layer — and that is what we build.

What we build

One graph, four layers

We treat the estate as a single graph. Each layer contributes edges, and each edge is decided by the engine that owns that layer. A property is a question about the graph, written in your own vocabulary before any analysis runs — so nobody can say the goalposts moved. Layer 1 is hosting-independent — it reads the app's own configuration — so it applies unchanged to an on-prem or self-hosted application; the cloud layers simply re-express against the host's own accounts and network when there is no cloud.

Layer 1 · the layer no product reads

Application authorisation

The app's own roles, API tokens and public access, exported read-only and translated into Cedar, then decided by its symbolic compiler. For the first time the application's permissions become an analysable object.

Engine · our translator + Cedar SymCC
Layer 2

Cloud IAM — or host account

Identity, resource and organisation policies, permission boundaries and session context — after everything that can narrow a grant has been applied. On an on-prem app this layer is instead the host service account, database credentials and secrets store the app runs under.

Engine · our IAM→SMT encoding, Zelkova as oracle
Layer 3 · the core of the product

Bridges

Where holding a permission in one layer effectively confers one in another — a plugin inheriting the app's cloud role, an identity-provider group mapping into both. Our catalogue, and the defensible part of the engine.

Engine · graph search, confirmed per path
Layer 4

Network

Whether the principal can actually reach the endpoint where a permission is exercised. A trust edge only matters if the path to exercise it exists.

Why now

The method was always right. Until recently it was not affordable.

Formal verification has been an expert-driven, costly and tedious exercise: somebody with formal-methods training has to model the system and write the specification by hand. That cost is the whole reason it stayed with the hyperscalers and the safety-critical industries, however much everyone else wanted the assurance.

Then

  • Weeks of specialist time to model one system
  • A scarce skill, priced accordingly
  • Economic only where failure is unaffordable

Wanted widely. Adopted narrowly.

Now

  • A model reads policies, role exports and configuration at machine speed
  • It proposes structure the expert reviews, corrects and rewrites
  • The expensive step collapses; the expert judgement stays
The method is finally affordable at the same moment the problem became unavoidable.

The division of labour

  • The expert drafts and ratifies every specification
  • The model assists, and never delivers a verdict
  • The solver decides — it is the ground truth

Hallucination is bounded by construction, not by tuning.

Why this is the defensible use of AI in security. The dominant industry pattern asks a model for a security verdict and then manages its false positives — and the measured evidence above is that models score near zero on exactly this problem. Our architecture never lets the model deliver a verdict: a decision procedure with published semantics returns the answer, and the AI only reduces the human cost of reaching it. AWS validates the same pattern in its own products, pairing AI-assisted authoring with an SMT validation step.
The guarantee

Stated precisely, with its conditions — and its limits

If the analysis reports a property as holding, then for every request expressible in the modelled fragment, against the configuration exported at time T, the property holds. If it reports a violation, it returns a concrete counter-example.

The proof depends on three things: the encoder matches the service semantics, the solver is correct, and the export is complete
What holds

We will say

“For this property, over these layers, as configured at 14:00 today, no request exists that violates it. Here is the proof artefact, and here is how to re-run it.”

And: “Here is a request that violates it, step by step — each step checkable against the engine that produced it.”

What does not

We will never say

“Your application is secure.” “We replace your WAF.” “No escalation is possible.”

A proof about a policy does not show the code calls it. It does not address stolen keys, injection or memory-safety bugs. Where the root cause is code or key custody, our contribution is to bound the blast radius — after a compromise, the graph states exactly what the foothold can and cannot reach.

Preventive and detective are complementary. A proof does not replace testing, detection or monitoring. Everything outside the model — the asset nobody inventoried, the stack that drifted from its template, the third party with a VPN account — is exactly where your existing tooling earns its place. We name the boundary of the model in every report.
